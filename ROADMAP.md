# TMS — Роадмап и планы развития

Живой документ с планами развития системы. Ведётся по мере появления идей и решений.

**Как читать / вести:**
- Каждая фича имеет **статус**, **приоритет** и краткое обоснование «чем лучше, чем в Битриксе».
- Статусы: 🟢 `в работе` · 🟡 `запланировано` · 🔵 `идея` · ✅ `сделано` · ⚪ `отложено`
- Приоритет: `P0` (критично) · `P1` (высокий) · `P2` (средний) · `P3` (когда-нибудь)

- Изменения роадмапа фиксируем в конце файла («История изменений»).

## 🟡 Запланировано

### 1. Интеграция Битрикс24 ↔ TMS ↔ 1С:УНФ — `P1`

Связка трёх систем по принципу «каждая система — хозяин своих данных».

**Источники истины:**

| Сущность | Источник истины | Реплика |
|---|---|---|
| Клиенты / контрагенты | Битрикс24 | TMS, 1С |
| Каталог товаров, цены | 1С:УНФ | TMS, Битрикс |
| Сделки | Битрикс24 | → TMS (заказ) |
| Заказы / отгрузки | TMS | → 1С (накладная) |
| Счета / оплаты | 1С:УНФ | → TMS (статус) |
| Складские остатки | 1С:УНФ | → TMS (только чтение) |

**Поток данных:** `Битрикс24 → TMS → 1С:УНФ`, обратно в TMS возвращаются оплаты и остатки.

**Интеграционные точки:**
- **Битрикс24 → TMS:** вебхуки Битрикса → `POST /api/integrations/bitrix/...` (сделка «Выиграна» → заказ; новый клиент → контрагент). Новый роутер `app/routers/integrations.py`.
- **TMS → 1С:УНФ:** OData API 1С (заказ «Отгружен» → расходная накладная; лограсходы → статья затрат).
- **1С:УНФ → TMS:** поллинг OData (1С не умеет вебхуки) через APScheduler — статус оплаты счёта (раз в час), остатки (раз в час), каталог (раз в сутки).

**Открытые вопросы (нужно решить до старта):**
1. Счета: TMS создаёт и пушит в 1С, или 1С создаёт, а TMS только читает статус?
2. Склад: оперативный склад в TMS + бухгалтерский в 1С, или всё в 1С (TMS только читает)?
3. Клиенты: единственная точка входа — Битрикс, или двусторонняя синхронизация с риском петель?

**Подготовка БД (уже проработано):** добавить поля `external_id_1c` и `synced_*_at` в `counterparties / products / orders / invoices / stock_movements`; настройки `onec_url/user/password/enabled` в `CompanySettings`.

**Документация:**
- [`docs/bitrix_tms_1c_integration.md`](docs/bitrix_tms_1c_integration.md) — архитектура связки, потоки, открытые вопросы.
- [`docs/1c_unf_integration.md`](docs/1c_unf_integration.md) — спека OData-интеграции с 1С:УНФ (миграции, модели, эндпоинты).

**Следующий шаг:** принять 3 архитектурных решения выше → начать с ветки «Битрикс → TMS» (создание заказа из выигранной сделки) как самой ценной и простой.

### 2. Клиентский портал по ссылке (трекинг заказа без логина) — `P1`

Клиент открывает персональную ссылку вида `https://tms.../track/<токен>` и видит статус своего заказа, отгрузки и документы — **без регистрации и без логина**.

**Чем лучше, чем в Битриксе:** Битрикс ради этого заставляет заводить экстранет-пользователей и логиниться. Здесь — ноль трения: отправил ссылку в WhatsApp/Telegram, клиент сразу всё видит. Это снимает поток звонков «а где мой заказ?».

**UX:**
- Публичная страница (без авторизации), только чтение.
- Показывает: номер заказа, текущий статус (с таймлайном этапов), состав/позиции, плановую дату отгрузки/доставки, ссылки на документы (счёт, договор), контакт менеджера.
- Адаптив под телефон, можно повесить PWA-иконку.

**Тех-эскиз:**
- Поле `public_token` (UUID/секрет, индекс) в модели `Order` — генерируется при создании заказа.
- Роут `GET /track/{token}` — **вне** `login_required`, отдаёт минимальный шаблон только с безопасными полями (не светим внутренние цены закупки, маржу, заметки).
- Кнопка в карточке заказа «Скопировать ссылку для клиента» + быстрая отправка в Telegram-бот.
- Безопасность: токен длинный и неугадываемый; rate-limit на эндпоинт; никаких внутренних данных; опционально срок жизни ссылки и возможность отозвать.

**Следующий шаг:** добавить `public_token` в `Order` (миграция + модель) → публичный роут и шаблон → кнопка «ссылка для клиента» в UI заказа.

### 3. Хранилище файлов в карточках контрагентов и заказов — `P1`

Возможность прикреплять документы прямо к карточке контрагента или заказа — с классификацией по типу и автоматическим сжатием при загрузке.

**Контрагенты — типы файлов:**
- Договор
- Доп. соглашение
- Прочее

**Заказы — типы файлов:**
- Счёт
- УПД (универсальный передаточный документ)
- ТН (товарная накладная)
- Прочее

**Требования к хранилищу:**
- Форматы: PDF и Word (`.docx`, `.doc`)
- **Сжатие при загрузке:** PDF сжимается (ghostscript или pikepdf), Word — конвертируется в PDF и сжимается. Цель: уменьшить размер в 2–5× без потери читаемости.
- Файлы хранятся в `uploads/{counterparties|orders}/{id}/` на сервере
- Максимальный размер до сжатия: настраивается (по умолчанию 20 МБ)
- В карточке: список файлов с именем, типом, датой загрузки, размером (до и после сжатия), кнопками «Скачать» и «Удалить»
- Загрузка нескольких файлов за раз (drag & drop или кнопка)

**Тех-эскиз:**
- Модель `AttachedFile`: `id`, `entity_type` (`counterparty` / `order`), `entity_id`, `file_type`, `original_name`, `stored_path`, `size_original`, `size_compressed`, `uploaded_at`, `uploaded_by`
- Роутер `app/routers/files.py`: `POST /files/upload`, `GET /files/{id}/download`, `DELETE /files/{id}`
- Фоновое сжатие: после записи файла на диск → `pikepdf` (PDF) или `python-docx` → PDF → `pikepdf` (Word). Не блокирует ответ — через `BackgroundTasks` FastAPI
- При удалении контрагента или заказа — каскадное удаление файлов с диска

**Следующий шаг:** создать модель `AttachedFile` + миграция → роутер upload/download/delete → виджет в шаблонах карточки контрагента и заказа.

## 🔵 Бэклог идей (из брейншторма, ждут приоритизации)

- **Отчёт выручки: прогноз выполнения плана** `P1` — рядом с текущим % плана показывать «при текущем темпе закроем на X%». Линейная экстраполяция: `факт / прошедшие_дни × дни_месяца`. Все данные уже есть — это минимум кода, максимум пользы для руководства.
- **Отчёт выручки: сравнение период к периоду** `P1` — текущий месяц vs тот же месяц прошлого года (и аналогично для недели/квартала). Показывает реальный рост бизнеса без влияния сезонности.
- **Отчёт выручки: разбивка по клиентам** `P1` — вкладка/секция «по клиентам»: кто сколько принёс за выбранный период, доля в выручке (%), изменение к предыдущему периоду. Сразу видно кто растёт, кто падает.
- **Отчёт выручки: экспорт в Excel** `P2` — кнопка «Скачать Excel» для таблицы отгрузок с KPI-шапкой. Нужна для отправки отчётов руководству. В `/leads` экспорт уже реализован — переиспользовать подход.
- **Отчёт выручки: понедельная гистограмма** `P3` — внутри месяца показывать динамику по неделям (не одно число, а 4–5 столбцов). Видно в какую неделю традиционно проседают продажи.
- **Квартальные планы** `P3` — дополнить страницу `/reports/plans` квартальными целями. Месячный план становится производным от квартального. Часто именно квартал ставится топ-менеджментом.
- **Редизайн вкладки «Выручка»** `P2` — текущая страница перегружена: KPI-карточки, таблица и фильтры свалены в кучу. Улучшения: вынести KPI в отдельный верхний блок с иконками и цветовыми акцентами; добавить мини-график тренда прямо в KPI-карточку; таблицу отгрузок сделать компактнее (убрать лишние колонки, добавить быстрые фильтры-чипы по статусу); вкладки «По заказам» / «По клиентам» / «По товарам» вместо одного длинного скролла; адаптив под мобильный (сейчас таблица ломается на телефоне).
- **Двусторонний Telegram-бот** `P1` — не только отчёты, но и управление: смена статуса, подтверждение заказа, дебиторка, алерты с кнопками действий. Инфраструктура бота уже есть.
- **ЛПР как отдельная сущность в прозвоне** `P1` — у одной точки несколько ЛПР (директор, закупщик, управляющий): имя, должность, личный телефон, email, Telegram/WhatsApp. История контактов отдельно по каждому ЛПР. При конвертации лида в контрагента — ЛПРы переносятся как контактные лица. Сейчас `contact_person` — просто текстовое поле, что не позволяет работать с сетями (один закупщик на 10 точек).

Менеджер нажал «Позвонил», выбрал результат, перешёл к следующему. Горячие клавиши для статусов. По окончании сессии — сводка: сколько обзвонено и с какими результатами. Редактируются в настройках, доступны всей команде. Поддержка переменных `{{name}}`, `{{category}}`. Выравнивает качество работы новых менеджеров.

- **Маркировка «Честный Знак»** `P3` — если продукция попадает под маркировку, станет киллер-аргументом против Битрикса.

Обновление по кнопке или раз в N часов. Статус СДЭК отображается в карточке заказа и, опционально, на странице публичного трекинга клиента.

- **Настройки: профиль пользователя** `P1` — страница `/profile`: смена пароля, имени. Сюда же поле дня рождения (для табло цеха).

- **Модульная система: включение/отключение блоков TMS** `P3` — флаги в настройках компании для каждого модуля (лиды, претензии, склад, табло цеха и др.); отключённые модули исчезают из меню и навигации. Позволяет упростить интерфейс под конкретный бизнес или убрать неиспользуемые разделы.
- **Склад: автосписание при сборке заказа** `P1` — при нажатии «Собран» автоматически создавать движения «out» по всем позициям заказа. Сейчас кладовщик делает это вручную отдельной формой. Связь `order_id` в `StockMovement` уже есть — нужна только логика в `mark_assembled`.
- **Склад: инвентаризация** `P1` — отдельная страница: вводишь фактические остатки по всем позициям сразу, система считает разницы и создаёт корректировки одним пакетом. Сейчас инвентаризацию делают через корректировки по одной позиции.

- **Склад: оборачиваемость и аналитика** `P2` — отчёт: сколько товара прошло за период, средний остаток, покрытие в днях («на сколько дней хватит при текущем темпе продаж»). Помогает планировать закупки.
- **Склад: партии и сроки годности (FEFO)** `P4` — учёт по партиям с датой изготовления и сроком годности, списание FEFO, алерты истечения. Актуально для пищёвки, но требует согласования процесса со складом и отлаженного производства. Возможно будет реализовано через 1С:УНФ в рамках интеграции.
- **Дебиторка: группировка по контрагентам** `P1` — сейчас строки по счетам, при нескольких счетах у одного клиента страница нечитаема. Нужно: «Клиент X — итого N₽, K просрочено» с раскрытием по клику. Сразу видно главных должников.
- **Договора: автоперевод в «Истёк»** `P1` — периодическая задача: `active` + `end_date < today` → `expired`. Аналогично уже реализованной авто-просрочке счетов.
- **Договора: уведомление об истечении** `P1` — за N дней до `end_date` уведомление в TMS и Telegram. N настраивается в настройках компании. Сейчас только цифра на дашборде.
- **Договора: статус подписания** `P2` — отдельный статус подписи: Черновик → Отправлен на подпись → Подписан нами → Подписан обеими сторонами. Независим от жизненного цикла договора.
- **Договора: комментарии и лог активности** `P2` — переиспользовать инфраструктуру `Comment` / `AuditLog` из заказов и КА.
- **Договора: расширенные фильтры** `P2` — диапазон дат, «истекают в ближайшие 30/60 дней», фильтр по типу оплаты.
