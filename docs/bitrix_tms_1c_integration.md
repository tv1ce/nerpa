# Интеграция Битрикс24 ↔ NERPA ↔ 1С:УНФ

> Статус: **NERPA ↔ 1С — реализовано** (см. раздел «Что уже готово»). **Битрикс ↔ NERPA — согласованная архитектура, ждёт двух уточнений со специалистом Битрикса** (каталог + код стадии «Подтверждён»).

---

## Принцип: NERPA — хаб, каждая система — хозяин своих данных

Битрикс и 1С **напрямую не общаются** — весь обмен идёт через NERPA. Это 2 канала интеграции вместо 3; 1С вообще не знает про существование Битрикса.

```
   КАРТОЧКА КЛИЕНТА + СДЕЛКИ          ЗАКАЗЫ / СКЛАД / ДОКИ        ФИНАНСЫ / БУХ
┌──────────────────────────┐    ┌──────────────────────┐    ┌──────────────────┐
│        БИТРИКС24          │◀──▶│         NERPA          │◀──▶│      1С:УНФ       │
│  (облако, хозяин клиента) │    │   (хаб интеграции)   │    │  (хозяин денег)   │
└──────────────────────────┘    └──────────────────────┘    └──────────────────┘
        вебхуки REST                                          OData + расширение
```

У каждой сущности один хозяин, остальные держат реплику, связанную через `external_id_*`. Это не дублирование, а кэш с единственным источником правды.

| Сущность | Источник истины | Реплика |
|---|---|---|
| Клиент + реквизиты (ИНН/КПП/банк) | **Битрикс24** | NERPA, 1С |
| Сделка | **Битрикс24** | → NERPA (заказ) |
| Каталог товаров, цены | **1С:УНФ** | NERPA, Битрикс |
| Заказ / состав / отгрузка | **NERPA** | → 1С (накладная), → Битрикс (статус) |
| Счёт / оплата | **1С:УНФ** | → NERPA → Битрикс |
| Складские остатки | **1С:УНФ** | → NERPA (чтение) |

---

## Два встречных потока (не конфликтуют)

```
ДОКУМЕНТЫ (вниз):     Битрикс ──сделка──▶ NERPA ──заказ/накладная──▶ 1С
СПРАВОЧНИКИ (вверх):  1С ──каталог/цены/остатки──▶ NERPA ──▶ Битрикс
ФИНОБРАТКА (вверх):   1С ──оплата──▶ NERPA ──▶ Битрикс
СТАТУС (вверх):       NERPA ──статус заказа──▶ Битрикс
```

Документооборот течёт вниз, справочники/деньги/статусы — вверх. Ни одно поле не пишется двумя системами → петель нет by design.

## Что уже готово: NERPA ↔ 1С (в коде)

Реализовано в [`app/services/onec_client.py`](../app/services/onec_client.py), роутер [`app/routers/sync_1c.py`](../app/routers/sync_1c.py), автополлинг каждые 15 мин (APScheduler, [`app/main.py`](../app/main.py)).

**NERPA → 1С** (триггерно, в фоновом потоке при сохранении):
- Контрагенты (`push_counterparty`) — с банковским счётом, видом ИП/ООО/физ, дедупом по ИНН.
- Договоры (`push_contract`).
- Заказы (`push_order`) при подтверждении — табличная часть «Запасы».
- Склад in/adjustment (`push_stock_movement`); out с заказом 1С создаёт сама.

**1С → NERPA** (поллинг):
- Номенклатура (линковка существующих, новые не создаёт).
- Счета (`sync_invoices_from_1c`) — 1С хозяин, NERPA читает + позиции.
- Оплаты → `Invoice.status=paid` + статус заказа.
- Расходные накладные → `order.shipment_id_1c`.
- Печатные формы (Счёт/УПД PDF, УПД XML) из расширения 1С → вложения заказа.

**Архитектурные вопросы из старого черновика — решены:** счета ведёт 1С (NERPA читает); склад — оперативка в NERPA, итог в 1С; клиент создавался в NERPA → 1С (теперь, с приходом Битрикса, точка входа сдвигается влево, см. ниже).

## Битрикс ↔ NERPA — проектирование (Сценарий A: Битрикс — хозяин клиента)

### Единый триггер: сделка «Подтверждён» создаёт контрагента + заказ

Контрагент в NERPA рождается **не на каждый контакт**, а только когда выполнены **оба** условия:
1. карточка контрагента в Битриксе заполнена (есть реквизиты);
2. сделка переведена в стадию «Подтверждён».

```
Лид ──конвертация──▶ Компания + Сделка
        │                                  │
   реквизиты заполнены        И      стадия «Подтверждён»
        └─────────────────┬───────────────┘
                          ▼
        Вебхук Битрикса ONCRMDEALUPDATE → NERPA
                          ▼
       POST /api/integrations/bitrix/deal:
         1. контрагент (поиск в 1С/NERPA по ИНН, без дублей)
         2. заказ из товарных позиций сделки
         3. существующий push в 1С (как сейчас)
```

Один триггер несёт и клиента, и заказ. Никаких полусырых лидов в NERPA, никакого мусора в 1С.

### Гейт реквизитов (обязателен)

Перед созданием NERPA проверяет минимум: **ИНН + банк (расчётный счёт + БИК)**. Нет — заказ не создаётся, в сделку Битрикса возвращается пометка «нет реквизитов». Защищает 1С, которой ИНН обязателен для документов.

### Обратная связь в Битрикс

NERPA пишет в карточку сделки (`crm.deal.update` / таймлайн):

| Событие | Откуда | Поле в сделке |
|---|---|---|
| Заказ собран / отгружён / доставлен | NERPA | `UF_TMS_СТАТУС` |
| Оплачено | 1С → NERPA → Битрикс | `UF_TMS_ОПЛАЧЕН` (транзитом; 1С Битрикс не дёргает) |
| Счёт/УПД PDF готов | 1С → NERPA → Битрикс | ссылка/файл в таймлайне |

**Защита от петли:** статусы пишутся в отдельные пользовательские поля (`UF_TMS_*`), **не** в стадию воронки. Триггер создания заказа слушает только стадию «Подтверждён». Читаемое и записываемое поля разные → обратная запись не вызывает повторного создания заказа.

### Каталог в Битриксе — НА УТОЧНЕНИИ (вопрос со специалистом)

Чтобы состав заказа ушёл в 1С с корректными GUID, товарные позиции сделки должны быть реальными SKU. Тогда нужна репликация каталога `1С → NERPA → Битрикс` (`crm.product`).
- **Вариант 1:** продажники выбирают SKU из каталога → нужна репликация каталога вверх.
- **Вариант 2:** состав пишется текстом, менеджер NERPA собирает заказ → каталог в Битриксе не нужен; непривязанные позиции уходят в комментарий заказа (поведение уже есть в `push_order`).

> ⏳ Решается на созвоне со специалистом Битрикса.

## Право собственности на поля

| Данные | Хозяин | Направление синхронизации |
|---|---|---|
| Карточка клиента + реквизиты | Битрикс | строго вниз: Битрикс → NERPA → 1С |
| Каталог, цены | 1С | строго вверх: 1С → NERPA → Битрикс |
| Заказ, состав, отгрузка | NERPA | → 1С, статус → Битрикс |
| Счёт, оплата | 1С | → NERPA → Битрикс |
| Статус заказа | NERPA | → Битрикс |

Существующий `push_counterparty` переиспользуется без изменений — данные теперь приходят из Битрикса, а не из ручного ввода в NERPA.

## Прозвон / лиды в NERPA → отключаемый модуль

Раз воронка переезжает в Битрикс, модуль прозвона/лидов NERPA дублирует функцию. Решение: **сделать его отключаемым модулем** (флаг в `CompanySettings`, скрытие из меню/навигации) с возможностью полного удаления в будущем. Связано с бэклог-идеей роадмапа «Модульная система: включение/отключение блоков NERPA».

## Технические изменения в NERPA

- Поля БД: `external_id_bitrix` на `counterparties` и `orders` (по аналогии с `external_id_1c`).
- `CompanySettings`: `bitrix_webhook_url` (входящий вебхук Битрикса для исходящих REST-вызовов), `bitrix_enabled`, код стадии «Подтверждён», карта `UF_*`-полей.
- Новый роутер `app/routers/integrations.py`: `POST /api/integrations/bitrix/deal`.
- Исходящие вызовы Битрикса — в фоновом потоке (`threading.Thread(... daemon=True)`), как уже сделано для 1С.
- Флаг отключения модуля прозвона/лидов в `CompanySettings`.

## Открытые вопросы (на созвон со специалистом Битрикса)

1. ⏳ **Каталог в Битриксе** — продажники выбирают SKU (нужна репликация каталога вверх) или пишут текстом?
2. ⏳ **Стадия «Подтверждён»** — точный код/идентификатор стадии сделки в боевом Битриксе для маппинга триггера.

Зафиксировано: реквизит-гейт = **ИНН + банк**; модуль прозвона/лидов → **отключаемый**.

## Порядок реализации (read-only first)

1. Поля БД (`external_id_bitrix`) + настройки Битрикса в `CompanySettings` + UI.
2. Приём вебхука `POST /api/integrations/bitrix/deal` (лог без записи) — отладить формат.
3. Создание контрагента из сделки (гейт ИНН+банк, дедуп по ИНН, переиспользуя `push_counterparty`).
4. Создание заказа из товарных позиций сделки → существующий `push_order` в 1С.
5. Обратная связь NERPA → Битрикс (статус заказа, оплата) в `UF_*`-поля.
6. Каталог 1С → NERPA → Битрикс — **после уточнения вопроса №1**.
7. Прозвон/лиды NERPA → отключаемый модуль.

---

## Риски и решения

| Риск | Решение |
|---|---|
| Дубли контрагентов | Поиск по ИНН перед созданием (уже есть для 1С) |
| Петля Битрикс↔NERPA по статусам | Статусы в отдельные `UF_*`-поля, триггер слушает только стадию |
| Сделка без реквизитов | Гейт ИНН+банк; возврат пометки в сделку |
| Непривязанные товары в заказе | Каталог в Битриксе из реплики 1С (вопрос №1) |
| Идемпотентность | `external_id_bitrix` / `external_id_1c` как ключи |
