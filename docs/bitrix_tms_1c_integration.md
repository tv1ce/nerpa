# Интеграция Битрикс24 ↔ TMS ↔ 1С:УНФ

> Статус: **черновик** — требует принятия архитектурных решений (см. раздел «Открытые вопросы»)

---

## Принцип: каждая система — хозяин своих данных

| Сущность | Источник истины | Реплика |
|---|---|---|
| Клиенты / контрагенты | **Битрикс24** | TMS, 1С |
| Каталог товаров, цены | **1С:УНФ** | TMS, Битрикс |
| Сделки | **Битрикс24** | → TMS (заказ) |
| Заказы / отгрузки | **TMS** | → 1С (накладная) |
| Счета / оплаты | **1С:УНФ** | → TMS (статус) |
| Складские остатки | **1С:УНФ** | → TMS (только чтение) |
| Логистические расходы | **TMS** | → 1С (статья затрат) |

---

## Поток данных

```
Битрикс24 ──→ TMS ──→ 1С:УНФ
    ↑                    │
    └────────────────────┘
      (оплаты, остатки обратно)
```

---

## Интеграционные точки

### 1. Битрикс24 → TMS

| Событие | Триггер | Действие в TMS |
|---|---|---|
| Сделка переведена в «Выиграна» | Вебхук Битрикса | Создать заказ |
| Новый клиент / изменение реквизитов | Вебхук Битрикса | Создать / обновить контрагента |

Механизм: **вебхуки Битрикса** → эндпоинт TMS (`POST /api/integrations/bitrix/...`)

### 2. TMS → 1С:УНФ

| Событие | Триггер | Действие в 1С |
|---|---|---|
| Заказ переведён в «Отгружен» | Смена статуса в TMS | Создать расходную накладную |
| Логистические расходы | Ручной ввод / импорт | Провести статью затрат |

Механизм: **OData API 1С** (спека: `docs/1c_unf_integration.md`)

### 3. 1С:УНФ → TMS

| Данные | Периодичность | Действие в TMS |
|---|---|---|
| Статус оплаты счёта | Поллинг раз в час | Обновить `Invoice.status = paid` |
| Складские остатки | Поллинг раз в час | Обновить `Product.stock` |
| Каталог товаров / цены | Поллинг раз в сутки | Синк `Product` |

Механизм: **TMS поллит OData 1С** (не вебхуки — 1С:УНФ их не поддерживает)

## Открытые вопросы

Перед реализацией нужно принять три решения:

### ❓ 1. Счета — кто создаёт?

**Вариант A:** TMS создаёт счёт → пушит в 1С (текущее поведение + синк)
**Вариант B:** 1С создаёт счёт → TMS только читает статус (TMS перестаёт быть финансовой системой)

Вариант B чище архитектурно, но требует переделки UI в TMS.

### ❓ 2. Склад — где вести?

**Вариант A:** TMS ведёт оперативный склад (SpockMovement), 1С — бухгалтерский
**Вариант B:** Склад полностью в 1С, TMS только читает остатки

Вариант B убирает дублирование, но TMS теряет возможность моментально реагировать на отгрузку.

### ❓ 3. Клиенты — точка входа?

**Вариант A:** Новые клиенты создаются в Битриксе → синкаются в TMS (Битрикс — источник истины)
**Вариант B:** Клиентов можно создавать и там и там, с двусторонней синхронизацией

Вариант A проще, вариант B — риск конфликтов и петель синхронизации.

## Технологический стек интеграции

- **Битрикс24 → TMS:** REST-вебхуки Битрикса, новый роутер `app/routers/integrations.py`
- **TMS → 1С:** OData HTTP-запросы (уже проработано в `docs/1c_unf_integration.md`)
- **1С → TMS:** фоновый планировщик (APScheduler, по аналогии с Telegram-ботом)
- **Авторизация:** токены в `.env`, не хранить в БД открытым текстом
