# Вебхук статусов перевозки: Метафора → TMS

Документ для перевозчика. Настраивается один раз в сценарии Метафоры: на смене
статуса рейса дёргается HTTP-запрос в TMS, и заказ автоматически меняет статус.

---

## Что нужно сделать

Отправлять `POST`-запрос на адрес ниже при каждой смене статуса заказа.

```
POST https://nuttshell.ru/api/metafora/status?key=<КЛЮЧ>
Content-Type: application/json
```

Ключ выдаёт менеджер TMS (он же — секрет; не публиковать). Вместо `?key=` можно
передавать его заголовком `X-TMS-Key: <КЛЮЧ>` — как удобнее в Метафоре.

### Тело запроса

```json
{
  "order": "80",
  "status": "доставлено",
  "comment": "принял Иванов"
}
```

| Поле | Обязательное | Что это |
|---|---|---|
| `order` | да, если нет `address` | Номер заказа в TMS. Принимается как «80», «№80», «0080» |
| `address` | да, если нет `order` | Адрес доставки — по нему заказ найдётся, если номера нет под рукой |
| `status` | да | Статус (см. таблицу ниже) |
| `comment` | нет | Произвольный комментарий, попадёт в журнал заказа |
| `carrier_inn` | нет | ИНН перевозчика — сужает поиск, если по адресу несколько заказов |

Номер заказа надёжнее адреса: по адресу может оказаться несколько активных
заказов, и тогда TMS ничего не изменит (см. «Ответы»).

### Статусы

| Что присылать | Что произойдёт в TMS |
|---|---|
| `доставлено`, `доставлен`, `выполнено`, `завершено`, `вручено`, `delivered`, `done` | Заказ закрывается — статус «Доставлено» |
| `в пути`, `забрал`, `отгружено`, `принят`, `на доставке`, `in_transit`, `picked` | Заказ переходит в «Передан поставщику» |

Регистр и точная формулировка не важны — TMS ищет слово по вхождению, так что
«Доставлено клиенту» или «Заказ в пути» тоже подойдут.

Отмену и возврат по вебхуку TMS не проводит: такие случаи разбирает менеджер
вручную. Если прислать неизвестный статус, заказ останется как есть, а в ответе
придёт `unknown_status`.

---

## Ответы

Всегда `HTTP 200` с JSON, кроме ошибок доступа. Поле `ok` — сработало или нет,
`message` — человекочитаемое объяснение, его можно показывать в Метафоре.

```json
{"ok": true, "reason": "ok", "message": "Заказ №80: Передан поставщику → Доставлено.", "order": "80", "status": "delivered"}
```

| `reason` | Значение |
|---|---|
| `ok` | Статус изменён |
| `order_not_found` | Заказ не найден — проверьте номер или адрес |
| `ambiguous` | По адресу несколько активных заказов — пришлите `order` |
| `unknown_status` | Статус не распознан, заказ не тронут |

Коды ошибок доступа: `401` — неверный или отсутствующий ключ, `503` — приём
статусов на стороне TMS не включён (сообщите менеджеру).

Повторный запрос с тем же статусом безопасен: TMS ответит, что заказ уже в этом
статусе, и ничего не изменит.

---

## Проверка связи

Перед настройкой сценария удобно убедиться, что ключ рабочий:

```
GET https://nuttshell.ru/api/metafora/ping?key=<КЛЮЧ>
```

Ответ `{"ok": true, "message": "TMS на связи, ключ верный"}` — можно настраивать.

## Пример запроса целиком

```bash
curl -X POST "https://nuttshell.ru/api/metafora/status?key=<КЛЮЧ>" \
  -H "Content-Type: application/json" \
  -d '{"order": "80", "status": "доставлено"}'
```

---

## Для стороны TMS

- Ключ — в `.env`, переменная `METAFORA_PUSH_KEY` (пусто = приём выключен, `503`).
- Разбор и смена статуса: [`app/routers/api_metafora.py`](../app/routers/api_metafora.py),
  общая с ботом логика поиска заказа — [`app/services/carrier_delivery.py`](../app/services/carrier_delivery.py).
- Каждый входящий вебхук пишется в лог целиком (`metafora: входящий вебхук {...}`) —
  если Метафора называет поля иначе, добираем синонимы в `_F_*` без правок на стороне
  перевозчика. Уже принимаются `order/order_number/номер_заказа/заказ`,
  `address/адрес/точка`, `status/статус/состояние`.
- Смена статуса проходит через общий `apply_status`: те же отметки времени
  (`handed_at`), запись в журнал заказа и пуш события в Bitrix24, что и при смене
  статуса руками в карточке.
